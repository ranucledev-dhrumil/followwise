## Goal
Schema for document requests and documents, a private storage layer behind an interface (Supabase or local/test), assigning checklists to parties, strictly validated uploads with versions, streamed downloads, and the free-tier limits. REST API only. Approve, reject, due date, cancel, purge and the derived filters come in PLAN-0013. No reminders, frontend, portal uploads, or antivirus.

## Decisions (append verbatim to README 14.1 as D-94 to D-100, table format of earlier rows)
D-94 Persistence (Flyway V9, JdbcClient, no JPA, RESTRICT foreign keys): document_requests(id uuid PK, workspace_id, app_id, party_id, checklist_id text, item_id text, label text, required boolean, expiry_days int null, due_date date null, status PENDING|RECEIVED|APPROVED|REJECTED, status_reason text null, current_document_id uuid null, approved_at timestamptz null, expires_on date null, version int not null default 1, created_by, updated_by, created_at, updated_at, cancelled_at null) and documents(id uuid PK, workspace_id, app_id, party_id, request_id uuid, version_no int, storage_key text null, original_filename text, content_type text, size_bytes bigint, sha256 char(64), uploaded_by, uploaded_at timestamptz default clock_timestamp(), purged_at timestamptz null). Composite foreign keys bind a request to its party and a document to its request, party, app, and workspace (same pattern as V7). Unique (app_id, party_id, checklist_id, item_id) among non-cancelled requests; unique (request_id, version_no). CHECKs: content_type in application/pdf, image/png, image/jpeg; size_bytes between 1 and 52428800; status in the four values; label 1 to 120 characters; status_reason not null only when REJECTED; expires_on not null only when APPROVED; storage_key is null if and only if purged_at is not null. A trigger allows an UPDATE of a documents row only when it sets purged_at from null and clears storage_key with every other column unchanged, and blocks every DELETE and TRUNCATE. request.current_document_id always refers to a non-purged document of that request. Dates are in the app time zone; timestamps in UTC.
D-95 Storage abstraction: interface DocumentStorage {put(key, bytes, contentType), open(key) returning an InputStream, delete(key)} with providers selected by STORAGE_PROVIDER=supabase|local. supabase uses the Supabase Storage HTTP API through java.net.http.HttpClient (no new dependency) against a PRIVATE bucket named STORAGE_BUCKET, with SUPABASE_URL and SUPABASE_SERVICE_KEY (server only, never logged, never sent to the browser). The key may be a new secret key (sb_secret_...) or a legacy service_role JWT: the client always sends it in the apikey header and sends Authorization: Bearer <key> ONLY when the key starts with "eyJ" (a legacy JWT); new secret keys are not JWTs and are never sent as Bearer. Timeouts: connect 5 s, request 30 s; one retry for GET and DELETE, none for PUT. local writes under STORAGE_LOCAL_DIR and is allowed ONLY in the local or test profile. Startup fails for: any other STORAGE_PROVIDER value; local outside local or test; supabase with a missing or non-https URL, key, or bucket. Storage keys are generated by the server as {workspaceId}/{appId}/{documentId} (UUIDs only, no user input). Tests never call the network: an in-memory fake and a contract test against a local JDK HttpServer that checks method, path, and headers.
D-96 Upload rules: raw-body upload (no multipart): POST .../document-requests/{requestId}/documents with the file bytes as the body, header X-Filename (URL-encoded, optional) and any Content-Type (ignored). MAX_DOCUMENT_BYTES (default 4194304) is enforced by Content-Length and by a counting wrapper that aborts the read; empty bodies are rejected. The type is detected from magic bytes (PDF %PDF-, PNG, JPEG) and only application/pdf, image/png, image/jpeg are accepted; the stored content_type is the detected one; the client-declared type and file extension are never trusted. The filename is sanitized (no path separators, control characters, or quotes; at most 100 characters; extension forced to match the detected type; default "document"), stored for display only, and never used in storage keys. The SHA-256 of the bytes is stored; an upload identical to the request's current document returns 200 with that document and creates nothing. At most MAX_CONCURRENT_UPLOADS (default 4) uploads run at once per instance; extra requests get 429 busy with Retry-After 5. Order: validate, put the object under a new random key, insert the row in one transaction, and delete the object (best effort) if the transaction fails.
D-97 Workflow: a checklist is assigned with POST .../parties/{partyId}/document-requests {checklistId}; it creates one PENDING request per non-archived item (label, required, expiry_days copied from the CURRENT definition; due_date = today in the app time zone plus dueOffsetDays when the item has one), skips items that already have a non-cancelled request (counted as skippedExisting), and rejects an unknown or archived checklist or one whose partyType differs from the party's type. Statuses: upload sets RECEIVED (also from REJECTED or APPROVED, clearing approved_at, expires_on, and status_reason); approve (only from RECEIVED) sets APPROVED with expires_on from the body, or today plus expiry_days when the item has expiry_days, or null; reject (only from RECEIVED, reason 1 to 200 characters) sets REJECTED; changing the due date and cancelling are separate actions. Every mutation carries expectedVersion and uses one conditional UPDATE (409 stale_version). Derived, never stored: overdue = required AND status in (PENDING, REJECTED) AND due_date before today; expired = APPROVED AND expires_on before today; expiring = APPROVED AND expires_on within N days.
D-98 Endpoints under /api/workspaces/{wid}/apps/{aid}: POST .../parties/{partyId}/document-requests; GET .../parties/{partyId}/document-requests; GET .../document-requests?status=&overdue=&expiringWithinDays=&partyId=&page=&size= (default size 20, maximum 50, ordered by due_date nulls last then id); GET .../document-requests/{rid} (with document version metadata, never storage keys); POST .../document-requests/{rid}/documents; GET .../documents/{docId}/download; POST .../document-requests/{rid}/approve {expectedVersion, expiresOn optional}; POST .../reject {expectedVersion, reason}; POST .../due-date {expectedVersion, dueDate}; POST .../cancel {expectedVersion} (OWNER); POST .../documents/{docId}/purge (OWNER; non-current versions only). Permissions: VIEW_DOCUMENTS (OWNER, STAFF), EDIT_DOCUMENTS (OWNER, STAFF: assign, upload, approve, reject, due date), MANAGE_DOCUMENTS (OWNER: cancel, purge). PORTAL_USER gets 403, non-members 404 (D-42). Writes on an archived app return 409 app_archived; assigning or uploading for an archived party returns 409 party_archived; reads still work. Every query scopes by workspace_id AND app_id (and by party and request for children). JSON bodies use the strict parser with an 8 KB limit; the upload path has its own limit (MAX_DOCUMENT_BYTES).
D-99 Free-tier guards (env vars with defaults): MAX_DOCUMENT_BYTES=4194304, MAX_DOCUMENTS_PER_APP=1000, MAX_STORAGE_BYTES_PER_APP=209715200 (non-purged documents), MAX_STORAGE_BYTES_TOTAL=943718400 (all apps, the database sum of non-purged size_bytes; a margin under the 1 GB free plan), MAX_VERSIONS_PER_REQUEST=10, MAX_REQUESTS_PER_PARTY=50, MAX_CONCURRENT_UPLOADS=4. Exceeding a limit returns 409 limit_exceeded (storage totals: 409 storage_full). Limits are checked after taking the app row lock (lock order: app, party, request) so concurrent uploads cannot exceed them. Startup validates the numeric settings with fixed-text errors.
D-100 Download and hygiene: downloads are streamed by the backend (the browser never receives storage URLs or keys), with Content-Type from the stored detected type, Content-Disposition attachment using an RFC 5987 encoded sanitized filename, X-Content-Type-Options nosniff, and Cache-Control private, no-store. Storage failures return 503 storage_unavailable (fixed text); a purged or missing object returns 410 gone. Logs and errors never contain filenames, file content, storage keys, party data, or storage responses; only counts and opaque ids. Antivirus scanning is not in v1 (known gap). Stored documents may contain personal data, so retention and deletion must be covered by the privacy policy work later.

## Facts the plan relies on (confirm; tests and the founder check prove reality)
